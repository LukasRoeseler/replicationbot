# Replication Bot

Bot that posts daily on Bluesky about a replication attempt and its outcome. This was created using Gemini-3.1-pro-preview and Claude Sonnet 5. The logo was created using ChatGPT 4.1 with a Gemini-prompt. The data used is the FORRT Library of Reproduction and Replication Attempts (CC-BY license). See here for up to date recommended citation: <https://github.com/forrtproject/FReD-data/blob/main/output/citation.txt>

Account: <https://bsky.app/profile/replicationbot.bsky.social>

## Reply bot

In addition to the daily broadcast (`bot.R`, its own workflow), `reply_bot.R` runs hourly (`.github/workflows/reply-bot.yml`, `0 * * * *`) and checks every candidate post against *both* a replication dataset and a retraction dataset:

- **Replications**: matches a DOI against `doi_o` in the FLoRA dataset, and replies with the outcome and a pointer to the corresponding [FLoRA Atlas](https://forrt.org/flora-replication-atlas/) entry — e.g. "Did you know there is a replication to this study? According to the replication authors, the replication attempt yielded mixed results.\n\nhttps://forrt.org/flora-replication-atlas/?dois=...". Outcome wording is shared with `bot.R` via `helpers.R`, so both keep the same voice.
- **Retractions**: matches a DOI against `OriginalPaperDOI` in the [Retraction Watch database](https://gitlab.com/crossref/retraction-watch-data) (CSV re-downloaded fresh on every run — updated weekly upstream) for rows where `RetractionNature` is `Retraction` or `Expression of concern` (other notice types, like `Correction`, are intentionally skipped — the two are distinguished in both the reply wording and the logged `notice_type`). Replies e.g. "Did you know that there is a retraction notice for this study? Reason: falsification/fabrication of data.\n\ndoi.org/...", where the link is always the notice's own DOI (`RetractionDOI`) — not the retracted paper's DOI — so it leads to the notice itself.

A post only ever gets one reply (replication is checked first, retraction second — relevant only for the rare case where a DOI appears in both datasets). Posts already replied to are tracked in one shared `replied_posts.csv` log (columns include `kind` and `notice_type` to tell the two apart, and `reply_uri` — the bot's own reply post — which `index.html` uses to fetch that conversation directly, since Bluesky's public API doesn't reliably list a fresh reply in the original post's replies).

Detection reads the DOI from a post's rich-text link facets (the real URL Bluesky stores even when it truncates the *visible* text to something like `doi.org/10.1207/s153...`), its external embed/link-card, and its plain text, in that order — so it isn't limited to only-visible-text links. Candidate posts come from three searches merged together (`collect_candidate_posts()` in `helpers.R`): one filtered to `doi.org` links, and two on topical keywords (e.g. "replicated OR replication OR reproduced", "retracted OR retraction OR \"expression of concern\"") with no link requirement at all — these catch a bare DOI typed with no link (e.g. "Has this study been retracted? 10.1006/obhd.1998.2802"), which the domain-filtered search alone would never surface as a candidate.

A separate, manually-triggered workflow, **`reply-bot-backfill.yml`**, runs the same `reply_bot.R` script with a 12-month lookback (`LOOKBACK_MINUTES=525600`) and a higher search limit (`SEARCH_LIMIT=2000`) instead of the usual 70 minutes/50 posts, to catch posts from before the hourly scan started. It's meant to be run once, on demand (`workflow_dispatch` only, no schedule), and shares the same `replied_posts.csv` dedup log as the regular scan. Note: Bluesky's search index may not surface every post from that far back equally well, and `sort = "latest"` means that if there are more than 2000 matching posts across the whole year, only the most recent ones within it are captured — this is best-effort, not a guarantee of finding everything.

Both workflows accept a `dry_run` input. In dry-run mode nothing is posted or added to `replied_posts.csv` — instead every match (post, DOI, kind, and the exact reply text that would have been sent) is written to `dry_run_preview.csv`, overwriting any previous preview, so a run's results can be reviewed before deciding to run it live.

Every run (live or dry) appends one row to `scan_log.csv` (`run_at`, `dry_run`, `candidates_scanned`, `replication_matches`, `retraction_matches`, `replies_posted`). The [stats page](stats.html) reads it to show all-time totals (posts scanned, matches by kind, replies posted) and a per-run history table.

**Trial period**: `reply_bot.R` is running a trial and stops replying automatically after 2026-08-05 (`EVALUATION_END_DATE`, defined in `helpers.R`; extended once already from an initial 2026-07-22 end date for another two weeks of regular runs), pending a decision on whether to keep it enabled. Remove that check (and the constant) once confirmed to stay — and update the matching note on the GitHub Pages site (`index.html`).

Known limitations:
- Can't verify computationally whether a given post is truly *about* the study vs. merely citing it in passing.
- If a study has more than one replication attempt or retraction record in the dataset, the reply reports the first matching row rather than summarizing all of them.
