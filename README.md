# Replication Bot

Bot that posts daily on Bluesky about a replication attempt and its outcome. This was created using Gemini-3.1-pro-preview and Claude Sonnet 5. The logo was created using ChatGPT 4.1 with a Gemini-prompt. The data used is the FORRT Library of Reproduction and Replication Attempts (CC-BY license). See here for up to date recommended citation: <https://github.com/forrtproject/FReD-data/blob/main/output/citation.txt>

Account: <https://bsky.app/profile/replicationbot.bsky.social>

## Reply bot

In addition to the daily broadcast (`bot.R`, its own workflow), `reply_bot.R` runs on its own schedule (`.github/workflows/reply-bot.yml`, every 15 minutes). It searches recent Bluesky posts linking to `doi.org`, checks whether the linked DOI is an original study (`doi_o`) that has a known replication in the FLoRA dataset, and if so replies with the replication's outcome and a pointer to the corresponding [FLoRA Atlas](https://forrt.org/flora-replication-atlas/) entry (e.g. "Did you know there is a replication to this study? According to the replication authors, the replication attempt yielded mixed results."). Posts already replied to are tracked in `replied_posts.csv` to avoid duplicate replies. Outcome wording is shared with `bot.R` via `helpers.R`, so both keep the same voice.

Detection reads the DOI from a post's rich-text link facets (the real URL Bluesky stores even when it truncates the *visible* text to something like `doi.org/10.1207/s153...`), its external embed/link-card, and its plain text, in that order — so it isn't limited to only-visible-text links. Candidate posts come from two searches merged together (`collect_candidate_posts()` in `helpers.R`): one filtered to `doi.org` links, and one on topical keywords (e.g. "replicated OR replication OR reproduced") with no link requirement at all — the second catches a bare DOI typed with no link (e.g. "Has this study been retracted? 10.1006/obhd.1998.2802"), which the domain-filtered search alone would never surface as a candidate.

A separate, manually-triggered workflow, **`reply-bot-backfill.yml`**, runs the same `reply_bot.R` script with a 4-week lookback (`LOOKBACK_MINUTES=40320`) and a higher search limit (`SEARCH_LIMIT=1000`) instead of the usual 20 minutes/50 posts, to catch posts from before the 15-minute scan started. It's meant to be run once, on demand (`workflow_dispatch` only, no schedule), and shares the same `replied_posts.csv` dedup log as the regular scan. Note: Bluesky's search index may not surface every post from weeks ago equally well, so this is best-effort, not a guarantee of finding everything.

## RetractionBot

`retraction_bot.R` (its own daily workflow, `.github/workflows/retraction-bot.yml`) works the same way as the reply bot above, but sourced from the [Retraction Watch database](https://gitlab.com/crossref/retraction-watch-data) (CSV re-downloaded fresh on every run, since the upstream data is updated weekly). It matches a post's DOI against `OriginalPaperDOI` for rows where `RetractionNature` is `Retraction` or `Expression of concern` (other notice types, like `Correction`, are intentionally skipped), and replies e.g. "Did you know that there is a retraction notice for this study? Reason: duplication of data. doi.org/...". Tracked in its own `retraction_replies.csv` log; shares `helpers.R`'s `normalize_doi()`/`extract_dois_from_post()`/`get_link()` and the same trial-period cutoff as the reply bot.

**Trial period**: both `reply_bot.R` and `retraction_bot.R` are running a one-week trial and stop replying automatically after 2026-07-22 (`EVALUATION_END_DATE`, defined once in `helpers.R`), pending a decision on whether to keep them enabled. Remove those checks (and the constant) once confirmed to stay — and update the matching note on the GitHub Pages site (`index.html`).

Known limitations:
- Neither bot can verify computationally whether a given post is truly *about* the study vs. merely citing it in passing.
- If a study has more than one replication attempt or retraction record in the dataset, the reply reports the first matching row rather than summarizing all of them.
